# Agent Behavior & Prompting Guidelines

## Context & Role

You are assisting with development of a personal portfolio website for a frontend developer. The project showcases projects, provides contact information, and features an AI chatbot. Your role is to:

1. **Maintain code quality** aligned with established patterns
2. **Enhance features** without breaking existing functionality
3. **Support rapid iteration** with clear, working code
4. **Follow conventions** so others (or future AI) can understand changes

---

## How to Approach Tasks

### For Bug Fixes
- Identify root cause first
- Check component lifecycle and dependencies
- Verify Tailwind classes and CSS variable usage
- Test in both development (`npm run dev`) and build (`npm run build`)
- Ensure no console errors

### For New Features
- Determine if new component or modification to existing is needed
- Follow component structure patterns (functional, hooks-based)
- Plan routing if pages are involved
- Consider responsive design from the start
- Add appropriate styling using Tailwind first

### For Styling Changes
- Use Tailwind utility classes
- Leverage existing CSS variables (`--color-bg`, `--generic-2`, etc.)
- Avoid adding new CSS files unless absolutely necessary
- Test on mobile, tablet, and desktop viewports

### For Firebase/Backend Changes
- Check that endpoint detection logic is correct (localhost vs production)
- Verify environment variables are properly configured
- Test Cloud Function locally before production changes
- Include error handling for API failures

---

## Key Behaviors to Adopt

### ✅ DO:
- Use Tailwind CSS for styling
- Keep components small and focused
- Write descriptive commit messages
- Run linting before committing
- Follow React Hooks patterns
- Use semantic HTML
- Think mobile-first for responsive design
- Reuse existing components when possible
- Document complex logic with comments
- Test changes locally before suggesting

### ❌ DON'T:
- Add CSS files without justification
- Create inline `<style>` tags
- Use hardcoded colors (use CSS vars)
- Ignore TypeScript for new files (use JSX)
- Modify package.json unnecessarily
- Leave console.errors or warnings
- Break existing routes or navigation
- Add dependencies without reason
- Over-engineer simple components
- Commit without running lint

---

## Task-Specific Guidance

### If asked to add a new project:
1. Update `projectData.js` with project metadata
2. Ensure image exists in `/public/` folder
3. Use ProjectCard component (already styled)
4. If project needs detail page: create in `/pages/ProjectPage.jsx` pattern
5. Verify link works (internal vs external)

### If asked to fix styling issues:
1. Inspect using browser DevTools
2. Check Tailwind class names for typos
3. Verify responsive breakpoints are correct
4. Look for CSS variable usage conflicts
5. Test on actual devices/viewports if possible

### If asked to improve chatbot:
1. Check Firebase endpoint configuration
2. Review error handling (currently minimal)
3. Add user feedback (loading states, error messages)
4. Consider message history limitations
5. Test API rate limiting

### If asked to add translations:
1. Add key-value pairs to `src/locales/en.json`
2. Use `useTranslation()` hook in components
3. Don't hardcode strings in JSX
4. Test with actual language content (not just keys)

### If asked to refactor code:
1. Preserve existing functionality
2. Update comments/docs if logic changes
3. Run full test suite (build + lint)
4. Keep commit history readable

## Communication Style

When proposing changes:
- **Be concise:** Explain what & why, not a 5-paragraph essay
- **Show examples:** Code is better than description
- **Ask clarifying questions** if requirements are ambiguous
- **Suggest alternatives** when multiple approaches exist
- **Highlight risks:** If a change could break something

---

## Testing Checklist Before Suggesting Changes

```
□ Component renders without errors
□ No console warnings/errors
□ Responsive design works (test at 375px, 768px, 1024px)
□ Tailwind classes are valid
□ CSS variables resolve correctly
□ Links work (internal & external)
□ ESLint passes: npm run lint
□ Build succeeds: npm run build
□ No breaking changes to routes
```

## File Naming & Organization

### Component Files
- **Pattern:** `PascalCase.jsx` (e.g., `MyComponent.jsx`)
- **Location:** `src/components/`
- **Export:** Default export

### Page Files
- **Pattern:** `PascalCase.jsx` (e.g., `HomePage.jsx`)
- **Location:** `src/pages/`
- **Route:** Add to `App.jsx`

### Utility Files
- **Pattern:** `camelCase.js` (e.g., `updateCalander.js`)
- **Location:** `src/utils/`
- **Export:** Named or default (consistent within file)

### Data Files
- **Pattern:** `camelCase.js` (e.g., `projectData.js`)
- **Location:** `src/projectData/`
- **Content:** Export as objects/arrays

## Commit Message Style

Use clear, descriptive commit messages:

```
feat: Add new project to portfolio
fix: Correct mobile nav spacing issue
style: Update button hover states with Tailwind
refactor: Simplify ChatBot message state logic
docs: Update component documentation
```

Include the Co-authored-by trailer:
```
git commit -m "feat: Add feature

Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>"
```

## Error Handling

When encountering issues:
1. **Read the error carefully** — error messages are usually helpful
2. **Check the component tree** — is parent passing correct props?
3. **Verify dependencies** — are all imports present?
4. **Test in isolation** — does the component work standalone?
5. **Check build output** — sometimes warnings become errors

---

## Performance Considerations

- Avoid unnecessary re-renders (use `useCallback`, `useMemo` when needed)
- Lazy load heavy images
- Keep component state minimal
- Avoid deep nesting of components
- Use React DevTools Profiler for bottlenecks

---

## Accessibility (a11y) Basics

- Use semantic HTML (`<button>` not `<div>` for buttons)
- Add `alt` text to images
- Ensure color contrast meets standards
- Make interactive elements keyboard accessible
- Use `aria-*` attributes where needed

---

## Questions Before Starting

If clarification is needed, ask:
- **Scope:** Is this a small fix or significant feature?
- **Dependencies:** Are other changes needed first?
- **Breakage:** Is it OK to modify existing code, or add-only?
- **Testing:** What should be tested to verify success?
- **Priority:** Is this urgent or can it wait?

---

**Remember:** The goal is to make the portfolio better while keeping it maintainable and understandable.
